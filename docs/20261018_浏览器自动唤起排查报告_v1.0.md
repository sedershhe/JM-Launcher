## 一、结论先行

**根因一句话**：`JML.exe` 这个**可执行文件本身带 Low 完整性标签**（整个工程目录被递归标成 Low），Windows 按官方规则「新进程完整性 = min(用户令牌, 映像文件标签)」把 JML 进程压到 Low；Low 进程调用 ShellExecute（`Process.Start(UseShellExecute=true)`、`cmd /c start`、`rundll32`、Python 的 `os.startfile` 是**同一条路径**）只会拉起一个**同样为 Low 的 msedge 启动器**，它无法把 URL 移交给用户已在运行的 Medium 浏览器实例，于是出现"调用成功、页面不出现、应用也不报错"。

**两个需要更正的前提**（都有实测支撑）：

1. 用户桌面会话本身**不是** Low：`explorer` 与本机 shell 都是 Medium。Low 来自**文件标签**，不是来自用户账户或桌面。
2. 建议里的"从普通桌面会话（Medium）启动"**在当前目录下无效**——用户本来就是双击启动（Medium 会话），是 exe 文件标签把进程压下去的。真正的最小修复是**把构建/发布目录的完整性标签改回 Medium**（或把程序复制到 Medium 目录再运行）。

**一句话建议**：先把 `bin\Debug\net10.0-windows`（或发布目录）的完整性标签恢复为 Medium 再启动；同时在代码里把"启动进程成功"与"浏览器真的打开了"区分开，Low 环境下直接引导用户复制链接。

## 三、机制解释（Windows 强制完整性控制 MIC）

### 3.1 三条规则（引用微软官方文档）

来源：[Mandatory Integrity Control - Win32 apps](https://learn.microsoft.com/en-us/windows/win32/secauthz/mandatory-integrity-control)

| 规则 | 原文（要点） | 对本问题的含义 |
|---|---|---|
| 进程完整性 = min(用户, 映像文件) | "the new process is created with the minimum of the user integrity level and the file integrity level"；"Processes you start ... receive your integrity level ... **or low if the executable file's level is low**" | 用户是 Medium，但 `JML.exe` 标签是 Low → 进程就是 **Low** |
| 无标签 = Medium | "Objects that lack an integrity label are treated as medium" | `%APPDATA%`、`%TEMP%` 没有 Low 标签 → 视为 Medium |
| 默认禁止向上写 | 对象 SACL 默认掩码 `SYSTEM_MANDATORY_LABEL_NO_WRITE_UP` | Low 进程写 Medium 对象 → **ACCESS_DENIED（0x80070005）**，即使 DACL 允许 |

### 3.2 为什么写不了 `%APPDATA%` / `%TEMP%`

`C:\Users\869**\AppData\Roaming`、`AppData\Local\Temp` 是 Medium（无标签按 Medium 算），JML 令牌是 Low。写操作按"禁止向上写"被拒，`CreateFile`/`File.WriteAllText` 抛 `UnauthorizedAccessException`，HResult 就是 `0x80070005`（E_ACCESSDENIED）。所以应用只能降级到 `ProgramDir`（该目录同为 Low，同级别可写）。

### 3.3 为什么 `UseShellExecute=true` 在 Low 下"成功但没打开"

拆成 5 步看：

1. JML（Low）调 `Process.Start(url, UseShellExecute=true)` → 进入 `ShellExecuteExW`。
2. Shell 解析 `http:` 关联（本机 `http` → `msedge.exe "%1"`，ProgId `MSEdgeHTM`）。
3. 系统创建 `msedge.exe` 进程：**父进程 Low → 启动器也 Low**（实测 2.3）。`ShellExecuteExW` 返回 TRUE，并把该进程句柄交给 JML。
4. 这个 Low 启动器按 Chromium/Edge 的**单实例**逻辑，要把命令行 URL 交给**已经在运行的 Medium 浏览器实例**（命名管道 / COM 单实例通道）。
5. 那个通道属于 Medium 进程的对象，Low 一侧写不进去（禁止向上写；跨完整性窗口消息另受 UIPI 限制）→ **URL 被静默丢弃，启动器退出 0**。

对 JML 来说，第 3 步就已经"成功"了，它根本看不到第 4～5 步失败，所以既不报错、也不会走下一级兜底。

> 说明：第 4～5 步的具体断点（管道还是 COM/窗口消息）是用行为证据推断的，未用 Procmon 抓包坐实，列在第七节"未验证项"。可确认的是：Low 下启动器确实是 Low、确实退出 0、确实没有导航；而 Low 的 Edge 独立实例能正常导航（2.7）。

### 3.4 `cmd /c start` 和 `rundll32` 在 Low 下会怎样

- 三者最终都落到同一套 Shell 协议解析 + 默认浏览器启动：
  - `cmd /c start "" <url>`：`start` 内部还是调 ShellExecute；cmd 子进程继承 Low。
  - `rundll32 url.dll,FileProtocolHandler <url>`：`FileProtocolHandler` 内部也是 ShellExecute；rundll32 子进程继承 Low。
- 所以它们**不会"绕过"限制**，只是把同一次失败换个进程重演：T3/T4 在 Low 下同样 `started=true`、`browser_hit=False`（2.2）。`rundll32` 在外层 cmd 里甚至返回退出码 0。
- 也不存在"被 UIPI 直接拦截并报错"的情况：拦在**移交**环节，调用方看到的是成功。

### 3.5 为什么手动粘贴 `http://127.0.0.1:<port>` 能打开

那是**已经在运行的 Medium 浏览器**自己去访问 loopback。JML 的低完整性只影响"它能不能把 URL 递给别人"，不影响它监听端口、也不影响别的进程访问这个端口。所以"服务本身没问题"与"JML 唤不起浏览器"可以同时成立。
