## 0. 一句话结论

**可行，但必须改动宿主（协议 + C# 渲染），纯插件侧做不出来。**

jmcomic 的搜索参数全部能透传，难点不在接口，而在「关键词输入框 + 折叠筛选区 + 80×110 结果行」这三样宿主插件页当前都不支持。建议新增 `search` 页面模板（不动现有 `list` 路径），配套新增折叠控件 `JmlCollapse`、宿主服务方法 `jm.search.search_advanced`、新插件 `plugins/advanced_search/`。

预期工作量：宿主 C# ≈ 900~1200 行，宿主 Python ≈ 250~350 行，插件 ≈ 500~700 行，协议文档 1 节。拆 5 个阶段，每阶段可单独验收。

## 2. 外部接口：jmcomic 能力实测矩阵

实测环境：D:/python/python.exe，jmcomic 2.7.1，2026-10-29 晚。脚本在 Draw/_probe*_20261029.py。

### 2.1 接口本体

JmSearchAlbumClient（D:/python/Lib/site-packages/jmcomic/jm_client_interface.py:312-408）只有一个底层方法：

```python
search(search_query: str, page: int, main_tag: int,
       order_by: str, time: str,
       category: str, sub_category: Optional[str]) -> JmSearchPage
```

外面包了 5 个便捷入口：search_site(0) / search_work(1) / search_author(2) / search_tag(3) / search_actor(4)。
`+ / - / 空格` 语义**由服务端解释**，客户端原样透传即可（实测确认）。

两个实现：

| 实现 | 类 | category | sub_category | time | 返回 total |
| --- | --- | --- | --- | --- | --- |
| API（默认） | JmApiClient（jm_client_impl.py:612） | 忽略 | 忽略 | 忽略 | ✅（>10000 封顶） |
| 网页 | JmHtmlClient（jm_client_impl.py:304） | ✅ | ✅ | ✅ | ⚠️ 旧正则失效，需自解析 |

### 2.2 实测结论（决定方案走向）

**API 通道**

- 五种 main_tag 全可用：search_site("全彩 -人妻") → total=10000；search_author("MANA") → 241；search_actor("神里绫华") → 145；search_work("MANA") → 1。
- 排序 mr/mv/mp/tf **真实生效**（同查询首 5 个 id 序列互不相同）。
- tr（评分）/ md（评论）不报错但**被忽略**，UI 不作为正式选项。
- time（t/w/m/a）**完全无效**：total 与 id 序列一模一样。
- category / sub_category **被忽略**：带不带分类结果完全相同。
- 无关键词的 categories_filter 分类浏览**分类生效**，但 sub_category 没进请求参数，无效。
- 结果**不含作者**（authors 全为 None）。

**网页通道**

- 域名是最大坑。JmModuleConfig.get_html_domain_all() 返回 9 个域名，2026-10-29 实测：
  - 18comic.vip 超时；18comic.ink SSL 重置；jmcomic-zzz.one / .org 403（Restricted Access）；
  - **comic18j-moco.work / comic18j-nico.site 200 可用**（jm365.work/3YeBdF 跳转到 moco）。
- **2026-11-08 复测（P1 探针 `Draw/20261108_搜索网页通道探针_v1.0.py`）**：三域全部 200 —— moco.work 2.17s（302 跳到 comic18j-nini.com）、nico.site 2.42s、ada.work 0.92s（上一轮没测，实际可用）。moco.work 已经是 302 跳 nini.com，而 `get_html_domain_all()` 动态列表里**不含** moco → 域名选择必须「动态列表优先 + 静态候选兜底」，不能只靠其中一种。
- 两个通道**搜索结果都不含作者**；网页条目里作者在别的节点，现有正则不取。
- time 在网页通道**生效**（t=w 时本页只有 27 条）。
- category / sub_category 在网页通道**生效**（/search/photos/doujin/sub/chinese 的 id 序列与不加子分类不同）。
- **total 解析失效**：pattern_html_search_total（jm_toolkit.py:495，正则 class="text-white">(\d+)</span> A漫.）匹配不到新版页面 → total 恒 0。
- 但页面里有新总数节点：`<span class="search-pagination-total"> 共257部 </span>`，可用 正则 `search-pagination-total">\s*共\s*(\d+)\s*\+?\s*部` 解析（实测 MANA 返回 257）。
- **2026-11-08 修正：网页 total 同样封顶 10000。** 总数 ≥ 10000 时页面显示「共10000+部」，分页 input 的 max=125，即网页通道同样是 10000 条 / 125 页封顶，**不是「不封顶」**。正则必须带可选中缀 `\+?`（只写 `(\d+)\s*部` 匹配不到「10000+部」），并记 `total_capped` 标志。
- **网页 total 常比 API 少**：实测作者 238 vs 241、登场角色 135 vs 145、站内 257 vs 263；同一关键词两通道的条目集合与顺序也可能不同（main_tag=0 时前 80 条只重合 65 条）。所以两通道结果**不许互相校验**，降级时也不要断言「total 应该相等」。
- **网页返回 0 条 ≠ 失败**：main_tag=1（作品范围）用「MANA -同人」时网页正常返回无结果页（total=0），API 也只有 1 条。判定成功要区分「页面正常但 0 结果」与「页面解析失败」：匹配到 total 节点或「无结果」文案 → 成功空结果；两者都没有 → 视为解析失败并降级。
- 条目解析仍可用（JmPageTool.parse_html_to_search_page 能返回 80 条 name/tags），只是 total 错。

### 2.3 由此确定的两条硬性设计

1. **双通道 + 能力自适应**：网页通道给全功能，API 通道兜底；UI 按通道把时间/分类/子分类置灰。
2. **结果行不显示作者**（两通道都没有），author 字段留空。

### 2.4 「优先网页通道」不是唤起浏览器（先讲清，避免误解）

| 说法 | 实际情况 |
| --- | --- |
| 不是 | 不是 `Process.Start` 打开系统默认浏览器，不弹任何窗口 |
| 不是 | 不是内嵌 WebView / CefSharp，不加载网页界面 |
| 不是 | 不启动本地 HTTP 端口（与 zip_web 插件的做法完全不同） |
| **是** | Python 后端用 `curl_cffi` 在**后台发一次 HTTP GET**，拿回 HTML 字符串，再用正则解析出条目 |

调用链：`JmcomicSource._search_html()` → `curl_cffi.requests.get(url)` → `JmPageTool.parse_html_to_search_page()` / 自写正则取总数 → 结构化 rows。

对用户来说观感与主搜索页一致，只多一次网络往返（本机实测 1~3 秒）。补充：jmcomic 自带的 `JmHtmlClient` 也是这个套路（`jm_client_impl.py:304`），只是它默认绑死第一个域名 `18comic.vip`（本机实测超时），所以我们要自己挑域名。

## 3. 方案选型

### 3.1 三个候选

| 方案 | 做法 | 回归风险 | 工作量 | 复刻度 |
| --- | --- | --- | --- | --- |
| **A（推荐）** | 新增 search 页面模板 + 折叠控件 JmlCollapse | 低（新分支，不碰 list） | 中高 | 高 |
| B | 给 list 加 search_box / collapsible / row_height 三个可选字段 | 中（改 RenderList，易碰坏现有 4 个插件） | 中 | 中 |
| C | 纯插件侧用 action 模板拼假搜索框 | 低 | 低 | 低（无输入框、无折叠、无法分页） |

**推荐 A**：语义清晰，以后做「排行榜/分类浏览」插件可复用，4 个既有插件零改动。

### 3.2 为什么不直接改 JmlCard 加 IsSwapped

PCL2 原版是整张卡折叠（标题行 40px + 箭头）。但本需求里**搜索卡不能折叠**（关键词框必须常显），折叠的是卡内「高级选项」区。改 JmlCard 得到的是整卡折叠，不匹配；且 Controls/JmlCard.xaml（104 行）目前无折叠代码，改它要动 4 个现有页面。

→ 新增独立控件 Controls/JmlCollapse.xaml（ToggleButton 头 + ContentPresenter + 高度补间），满足观感又不碰现有卡片。

## 5. 协议扩展设计：search 模板

### 5.1 与 list 的差异

- 继承 list 的：rows / page / page_size / total / total_pages / row_actions / row_double_click_action / empty_text
- 新增：search_box（关键词框）、filters（改为「暂存不下发」）、advanced（折叠区）、channel / capabilities / hint
- **filters 语义变化**：选中不重载，与关键词一起在「点搜索/回车」时提交。这是与 list 最大的行为差别，文档必须写死。

文件 Python/jml/core/jm_source.py（现有 search 在 :406，_ensure_client 在 :266）。新增：

```python

def search_advanced(self, *, keyword: str, page: int = 1,
                    main_tag: int = 0, order_by: str = "mr",
                    time: str = "a", category: str = "0",
                    sub_category=None, channel: str = "auto") -> dict:
    """
    强化搜索：双通道。
    channel=auto → 优先 html（功能全），失败降级 api（保底）。
    返回 {channel, capabilities, keyword, page, page_size, total,

```

内部三段：

1. _search_html(...)：用 curl_cffi 直接 GET
   https://{domain}/search/photos[/{category}[/sub/{sub}]]?main_tag=&search_query=&page=&o=&t=
   → PatternTool.require_match 缩短范围 + 条目正则解析 rows；
   → total 用自写正则 search-pagination-total">\s*共\s*(\d+)\s*\+?\s*部（必须带 \+?，网页同样 10000 封顶）；
   → 失败（超时/403/SSL）换下一个域名，全失败抛 ChannelUnavailable。
2. _search_api(...)：self._ensure_client().search(...) 全参数透传（现有 client 即可）。
3. 每条结果映射成与现有 search() 相同的行结构，避免 C#/插件二次清洗。

要点：

- 域名探测结果与通道可用性做 **60 秒模块级缓存**，避免每页探测。
- 网页与 API 通道 total **都封顶 10000**（网页显示「10000+部」、分页上限 125 页）；网页 total 常比 API 少几条（238/241 等），属镜像索引差异，不做对齐断言。
- category=="0" 时 URL 不带分类段；sub_category 仅在 category!="0" 时追加。
- **不在 jm_source 里做 UI 判断**（enabled/hint 由插件算）。

### 6.3 服务方法

Python/jml/services/host_services.py（jm.search 在 :95-113）新增 search_advanced：

```python
def _search_advanced(self, payload):
    source = get_source()
    return source.search_advanced(
        keyword=str(payload.get("keyword") or "").strip(),
```

### 8.2 main.py 骨架

```python
PAGE_ID = "advanced_search.main"
SEARCH_SERVICE, SEARCH_VERSION = "jm.search", 1

_FILTERS = [...]     # 5 个下拉的静态定义（options 与 capability 依赖键）
_DEFAULTS = {"keyword": "", "main_tag": "0", "order_by": "mr",
             "time": "a", "category": "0", "sub_category": ""}

def setup(ctx):
    ctx.register_page(PAGE_ID, load=page_payload, action=page_action)

def page_payload(ctx, params):
    state = _read_state(params)                  # 参数优先，其次 config 上次值，最后默认
    page = _positive_int(params.get("page"), 1)
    if not state["keyword"]:
        return _empty_payload(state, "输入关键词后点「搜索」", channel=None)
    data = ctx.call_service(SEARCH_SERVICE, SEARCH_VERSION, "search_advanced", {
        "keyword": state["keyword"], "page": page,
        "main_tag": int(state["main_tag"]), "order_by": state["order_by"],
        "time": state["time"], "category": state["category"],
        "sub_category": state["sub_category"] or None,
    })
    ctx.config_set("last_filters", {k: state[k] for k in _DEFAULTS if k != "keyword"})
    return _payload(state, data)

def page_action(ctx, action_id, payload):
    if action_id == "detail":
        return {"refresh": False, "data": {},
                "intent": {"type": "detail", "book_id": payload.get("book_id")}}
    if action_id == "download":
        return {"refresh": False, "data": {},
                "intent": {"type": "download", "book_id": payload.get("book_id")}}
    return {"refresh": False, "data": {}, "message": "未知操作"}
```

_payload(state, data) 负责把 capabilities 折进每个 filter.enabled/hint，并拼 advanced.summary（如「站内 · 最新」）。

### 8.3 子分类联动

sub_category 的 options 依赖 category：

- category=0 / single → 只留 --（或给 chinese/japanese/youth）
- category=doujin → 加 CG
- category=another → 加 other / cosplay / 3d
- 其余 → 只留 --

C# 在 RenderSearch 里重建下拉即可实现联动；但**重建会收起已展开的下拉**，所以 category 变更后不立即重载（语义就是「点搜索才生效」），子分类选项在下次提交后才刷新。文档写清楚。

## 15. 附：为什么不是「插件自己抓网页」

插件协议明确「不 import 宿主私有模块、不探测路径」（见 plugins/favorites/main.py 文件头）。抓网页需要域名探测、超时、降级、缓存，这些属于宿主能力；放在插件里会让每个搜索型插件各写一套，且绕过宿主统一的重试与日志。所以 search_advanced 放 jm_source，插件只做「参数校验 + payload 拼装」。
