## 二、插件依赖声明全为空数组 —— 根因分析

用户提出"后续全部通过插件添加"，因此先厘清旧项目该缺陷的根因。

### 现象
4 个插件的 `plugin.json` 中 `dependencies.plugins` 均为 `[]`，
但 `zip_web` 实际强依赖 `zip_browser` 的 `zip_archive.py`。

### 根因链（关键结论）
```
宿主隔离导入（只把插件自身目录放进虚拟包路径）
  → 插件之间无法互相 import
      → 开发者改用"按文件路径手工加载"绕过
          → 依赖不走清单、改走路径
              → 清单填了也没用 → 干脆全填空数组
```

**根因在第一步**：不是"开发者忘了填"，而是隔离导入导致跨插件 import 失败，
才逼出路径探测 + 硬编码兜底这一串权宜之计。

### 三重后果
1. 宿主的拓扑排序与依赖检测**从未真正生效**（只在单元测试跑过）
2. `zip_shared.py` 硬编码绝对路径 → 项目搬家即挂
3. 删除 `zip_browser` 会让 `zip_web` 不可用

### 对用户计划的致命性
"全部插件化"必然产生大量跨插件复用。若沿用旧机制，
每做一次复用就要重写一遍路径探测，且依赖顺序无保证、删插件无明确报错。
**因此必须先解决"插件之间如何复用代码"这个根因，再动手做插件体系。**

## 三、数据交换协议的优化方向（已与用户确认）

核心一条：**让插件既能"需要什么"，也能"提供什么"，全部走协议。**

| # | 优化项 | 解决什么 |
| --- | --- | --- |
| 1 | 服务注册表（最关键） | 主程序与插件均可注册服务；插件声明所需服务；宿主统一装配，缺失时明确报错 |
| 2 | 事件完整化 | 所有事件都有类型，禁止裸 dict（旧项目 `download.batch_finished` 就是裸 dict） |
| 3 | UI 扩展点扩充 | 在标签页/命令之外补充"设置项"与"通知提示" |
| 4 | 配置契约生效 | schema 真正用于默认值与校验，不再是纯文档 |
| 5 | 协议版本化 | 明确 API_VERSION 兼容策略，不匹配直接拒绝（用户已确认） |
| 6 | 依赖声明生效 | 拓扑排序 + 环检测 + 缺失明确报错（宿主本来就有这套代码，只是没被用起来） |

### 服务注册表如何解决跨插件复用（以 zip_web 依赖 zip_browser 为例）
```
zip_browser 声明：我提供 IArchiveReader 服务（版本 1）
zip_web     声明：我需要 IArchiveReader 服务（版本 1）
宿主启动：按依赖顺序先加载 zip_browser → 装配服务给 zip_web
         若前者缺失/被禁用 → zip_web 明确报"缺少服务"，而非崩溃
```
结果：消除路径探测、硬编码路径与空数组依赖声明。

### 克制边界（与"轻量简单"定位一致）
不做沙箱隔离、不做热插拔、不做跨版本自动适配。

## 四、图标素材的实测发现（阻塞项）

用户计划"采用 PCL2 启动器图标背景，文字改为 JML"。

**实测结论：本地 `PlainToolkit.UI` 仓库不含任何图片文件。**
- 仓库文件类型仅：`.xaml` / `.cs` / `.baml` / `.json` / `.md` / `.csproj` / `.slnx`
- 无 png / ico / svg / jpg / bmp 任何位图
- `Themes/Controls/Window.xaml` 仅为空模板（`AdornerDecorator` + `ContentPresenter`），无背景图案

因此"PCL2 启动器图标背景"在本地不存在，需用户二选一确认：
- **A**：指 PCL2 的界面布局风格（左侧导航 + 标题区），无需素材
- **B**：指某个具体图标素材文件，需用户提供路径或放入项目目录

在确认前，图标相关实现保持不动。旧项目根目录存在 `JMlogo.ico`（123,966 字节），
是否沿用亦待用户决定。
